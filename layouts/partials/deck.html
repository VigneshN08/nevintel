Indicators of Compromise

Handling rules

An indicator of compromise is an artefact that suggests a system was attacked — a file hash, a domain, an IP address, a URL. NEVINTEL currently extracts and displays CVE identifiers only, because that is the one class we can verify by construction: a CVE either appears in the text we hold or it does not. Live network indicators arrive in Phase 4, and these are the rules they will be published under.

hxxps://malicious-example[.]com/payload  ·  203[.]0[.]113[.]45  ·  user[@]phish[.]example

  1. 01 Always defanged, never clickable. Every indicator renders inside a code element with dots bracketed and http written hxxp. It is never wrapped in a link.
  2. 02 Because link previews fetch things. Slack, Teams, Discord and mail gateways pre-fetch URLs to build previews. A live indicator link means every paste of this page generates real requests to attacker infrastructure from readers' networks, attributed to them.
  3. 03 Defanged before storage, not before display. Doing it in client-side JavaScript means a failed script re-arms every indicator on the page.
  4. 04 Extracted, then proven. Regex sweeps broadly, then anything that does not appear verbatim in the source article is discarded. An indicator that is not a substring of the text cannot be real, and that single check removes the entire fabrication class.
  5. 05 Known-good suppressed first. MISP warninglists (public domain) filter CDN ranges, cloud providers, public resolvers and popular domains before anything is published, so 1[.]1[.]1[.]1 never gets flagged for matching a shape.
  6. 06 Hedged language, always. “Suspected”, “reported as”, “associated with” — never a flat assertion that a live business's domain is malicious. Indicators expire, and removal requests for remediated hosts are honoured.
  7. 07 No third-party verdicts republished. VirusTotal, AbuseIPDB, GreyNoise and urlscan all forbid public redisplay of their results. We link to those tools; we never mirror what they say.
